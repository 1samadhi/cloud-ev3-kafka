# Evidencia 55 · Las tres colas de RabbitMQ funcionando con mensajes reales

Fecha: 2026-11-26 04:46 (-03)
Entorno: **AWS**, instancia `i-0f5f47b9ffdefa327`, IP fija `18.211.30.140`
Origen del requisito: observación del docente en la EV2 — *"todas las colas
implementadas deben funcionar"*.

## Por qué hacía falta

Hasta ahora sólo `notificaciones.cliente` estaba verificada de punta a punta (la
prueba de humo la recorre en cada corrida). De las otras dos, el documento 17
decía textualmente: *"Un mensaje real llegando a un DLT o a la DLQ en el broker
(sólo en pruebas unitarias)"*. Es decir: la topología estaba declarada y los
consumidores existían, pero **nadie había visto un mensaje atravesarlas**.

## Qué se hizo

Se publicaron dos mensajes directamente al exchange `pedidos360.notificaciones`
por la API de management, con la misma routing key (`carrito.producto-agregado`):
uno válido y uno deliberadamente corrupto (`esto no es json`).

Publicar al exchange en vez de usar la tienda es a propósito: aísla el
comportamiento del broker y de los consumidores de cualquier lógica de negocio,
y permite provocar el mensaje "veneno" que de otro modo no se puede generar.

## Resultado

### 1 · `notificaciones.auditoria` — el binding `#` recibe TODO

El consumidor de auditoría registró **los dos** mensajes, el válido y el roto:

```
[AUDITORIA] routingKey=carrito.producto-agregado messageId=evid-ok-1795668384
            cuerpo={"idNotificacion":"evid-ok","usuarioId":"evidencia",...}
[AUDITORIA] routingKey=carrito.producto-agregado messageId=evid-roto-1795668384
            cuerpo=esto no es json
```

Esto demuestra lo que el contrato §9 justifica: un mismo mensaje llega a **dos
colas distintas** sin que el productor sepa cuántas hay, porque la cola cliente
se suscribe por patrón (`carrito.*`) y la de auditoría con `#`. La auditoría
registra incluso lo que la cola cliente no puede procesar, que es justamente
para lo que sirve.

### 2 · `notificaciones.cliente.dlq` — la cadena completa del mensaje muerto

El mensaje corrupto recorrió los cuatro pasos, cada uno con su registro:

```
ERROR RabbitConfig : Mensaje rechazado SIN reencolar -> DLX -> DLQ:
      cola=notificaciones.cliente routingKey=carrito.producto-agregado
      messageId=evid-roto-1795668384
      motivo=JsonParseException: Unrecognized token 'esto'

WARN  RecuperadorHaciaDlq : Retries exhausted for message
      (Body:'esto no es json' ... receivedDeliveryMode=PERSISTENT,
       redelivered=false, consumerQueue=notificaciones.cliente)

ERROR ConsumidorDlq : MENSAJE MUERTO en DLQ:
      colaOrigen=notificaciones.cliente motivo=rejected conteo=1
      exchangeOrigen=pedidos360.notificaciones
      routingKeys=[carrito.producto-agregado]
      messageId=evid-roto-1795668384 cuerpo=esto no es json
```

Lo que se comprueba en esa secuencia:

| Paso | Qué prueba |
|---|---|
| `JsonParseException` y agotar reintentos | el error se maneja en la aplicación, no se pierde |
| `rechazado SIN reencolar` | no hay bucle infinito de reentrega |
| `DLX -> DLQ` | la dead-letter exchange fanout está bien enlazada |
| `ConsumidorDlq` registra `colaOrigen`, `motivo` y `conteo` | los metadatos `x-death` sobreviven al viaje, que es lo que permite diagnosticar después |

### 3 · Estado de las tres colas al terminar

```
notificaciones.cliente       tipo=quorum  consumidores=1  mensajes=0
notificaciones.auditoria     tipo=quorum  consumidores=1  mensajes=0
notificaciones.cliente.dlq   tipo=quorum  consumidores=1  mensajes=0
```

Las tres son **quorum** y durables, las tres tienen consumidor activo, y
ninguna quedó con mensajes atascados: todo lo publicado se procesó.

## No verificado

- La caída de **un nodo** del clúster RabbitMQ con mensajes en vuelo (las colas
  son quorum con 3 réplicas, pero no se ha provocado la caída).
- El límite `x-delivery-limit = 5` del broker: aquí actuó primero el rechazo de
  la aplicación (`conteo=1`). Para verlo haría falta un consumidor que muera
  antes de poder rechazar.
- El comportamiento con la cola llena (`x-overflow = reject-publish`).
